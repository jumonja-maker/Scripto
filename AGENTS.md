# ScriptoLib — правила работы

## Поставка изменений

Пользователь 26 октября 2026 года разрешил после проверок сразу переносить законченные изменения в `main` и публиковать GitHub Release. Не оставлять готовую функцию только в Draft PR и не требовать от пользователя ручного слияния или повторной установки каждой версии. Это разрешение действует для последующих изменений ScriptoLib в рамках порученной задачи.

- Работать по RoadMap: одна функция, проверки, пользовательская проба, исправления, следующий шаг. Сохранять минималистичный интерфейс.
- Для каждого обновления приложения повышать `X.Y.Z` одновременно в `src/scriptolib/__init__.py`, `pyproject.toml`, пакете и теге `vX.Y.Z`.
- Публиковать стабильный GitHub Release в `jumonja-maker/Scripto`, доступный через `releases/latest`. Тестовый статус сборки и непроведённые Windows-проверки честно указывать в описании; не выдавать автоматические тесты за проверку на Windows.
- Прикладывать `ScriptoLib-X.Y.Z-Setup.exe`, `ScriptoLib-X.Y.Z-windows-x64.zip` и `SHA256SUMS.txt`. Одного установщика недостаточно для встроенного обновления.
- После публикации проверить название ZIP, размер и `digest: sha256:…` через GitHub API, а также распознавание релиза функцией `check_release` из предыдущей версии без установки.
- Не заменять уже опубликованные файлы молча: исправление приложения получает новый номер версии.
- Все управляемые приложением данные и временные файлы хранить внутри выбранной папки установки. Обновление и удаление должны сохранять `media` и внешние исходные медиафайлы.
- Не запускать платные или расходующие GitHub-hosted минуты workflow без отдельного основания. В M1 сборка выполняется локально; постоянный CI пока не настроен.

Если публикацию блокирует отсутствие нужной операции подключения или входа в GitHub, закончить независимую доступную работу, сохранить проверенные артефакты и ясно сообщить, что релиз ещё не опубликован. Не обещать доступность обновления по кнопке до проверки релиза.
