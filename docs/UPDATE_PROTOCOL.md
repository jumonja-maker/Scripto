# Обновление ScriptoLib

Этот протокол относится к установленной версии Windows x64. Кнопка проверки
обновлений в исходном checkout может проверять релизы, но не должна подменять
локальную среду разработчика.

## Папки и владение файлами

```text
ScriptoLib/
  ScriptoLib.exe
  current.txt
  .scriptolib-install.json
  versions/0.1.0/
    runtime/
    app/bootstrap.py
    app/src/scriptolib/
    scriptolib-package.json
    .scriptolib-version.json
    .scriptolib-owned.txt
  data/
  cache/
  media/
```

Все служебные записи обновления находятся в `cache/` выбранной папки. Установку
нужно размещать там, где пользователь имеет право записи. Код обновления не
использует системный TEMP, AppData или пользовательскую домашнюю папку. Он не
копирует, не перемещает и не удаляет `media/` или внешние медиафайлы.

Версия имеет строгий вид `X.Y.Z`. Канал обновления пока только стабильный:
предварительные релизы не устанавливаются.

## Пакет релиза

Источник метаданных: `https://api.github.com/repos/jumonja-maker/Scripto/releases/latest`.
Архив: `ScriptoLib-X.Y.Z-windows-x64.zip` в том же GitHub-репозитории.
GitHub API должен предоставить `digest: sha256:...` и точный размер asset.
Если контрольной суммы нет, автоматическое обновление прекращается.

ZIP содержит `runtime/`, `app/` и корневой `scriptolib-package.json`:

```json
{
  "format": 1,
  "application": "ScriptoLib",
  "version": "0.1.0",
  "files": {
    "runtime/pythonw.exe": "SHA256",
    "app/bootstrap.py": "SHA256"
  }
}
```

Поле `files`, когда присутствует, перечисляет все файлы ZIP, кроме самого
манифеста, с их SHA-256. Сборщик выпускает полный список. Проверяются SHA-256
всего ZIP и каждого перечисленного файла. Запрещены абсолютные пути, `..`,
обратные слеши, ссылки, специальные файлы, повторяющиеся имена с учётом регистра
Windows, зарезервированные имена Windows и любые корневые разделы кроме
`runtime/` и `app/`. Есть пределы размера скачивания, распаковки и числа файлов.

## Последовательность

1. `check_release(current_version)` только читает метаданные. Отсутствие
   опубликованных релизов (404) означает отсутствие обновления. Сетевая ошибка
   не мешает локальной библиотеке.
2. После отдельного действия пользователя `download_update(root, release)`
   скачивает ZIP в `cache/updates/`, проверяет размер и SHA-256. Уже проверенный
   ZIP повторно не скачивается. Незавершённый файл `.part` убирается при ошибке.
3. `stage_update(root, archive, release)` проверяет и распаковывает пакет в
   `versions/.stage-*`, затем атомарно переименовывает папку в `versions/X.Y.Z`.
   Активная версия пока не меняется. ZIP из собственного кеша удаляется как
   после успешной подготовки, так и при отказе проверки.
4. Пользователь нажимает «Обновить и перезапустить». Пока GUI удерживает
   `app.lock`, вызывается `prepare_restart(root, new_version)`. Транзакция
   `cache/update-pending.json` блокирует обычный параллельный запуск.
5. После `app.exec()`, остановки рабочих потоков и освобождения `app.lock`
   запускается **старый** встроенный Python:

   ```text
   pythonw.exe -B -m scriptolib.update_worker --root ROOT --version X.Y.Z --parent-pid PID --token TOKEN
   ```

   Родительский процесс завершает работу. Встроенный `python312._pth` включает
   `../app/src`, чтобы модуль находился без установки в системный Python.
6. Helper ждёт завершения родителя до 60 секунд. Затем атомарно меняет
   `current.txt` и запускает новый `app/bootstrap.py --root ROOT --update-token TOKEN`.
7. Новый процесс после успешного открытия базы, загрузки QML-окна и первого
   прохода цикла событий вызывает `mark_update_ready(root, token, version)`.
   Helper ждёт это подтверждение до 45 секунд. Сам факт создания процесса
   успешным обновлением не считается.
8. При отказе новая запущенная копия останавливается **до** возврата указателя.
   Затем восстанавливается предыдущая версия и запускается с тем же token.
   Если новый процесс не удалось остановить, автоматическая очистка/подмена
   прекращается до безопасного восстановления.
9. Только после завершения helper `finish_or_recover(root)` завершает транзакцию
   и убирает старую версию. Новое приложение может вызывать его таймером.

## Встраивание в запуск GUI

- Обычный запуск сначала вызывает `finish_or_recover(root)`, затем проверяет
  `launch_allowed(root)`. Если восстановление изменило `current.txt`, нужно
  перезапустить приложение через стабильный launcher вместо исполнения уже
  выбранной неудачной версии.
- Запуск с `--update-token` проверяет `launch_allowed(root, token)`, создаёт окно
  и базу, затем подтверждает готовность. Ещё до тяжёлых импортов Qt bootstrap
  вызывает `register_update_child(root, token)` и записывает PID запуска.
  До подтверждения он не вызывает
  восстановление своей транзакции.
- После здорового запуска без активного helper вызываются
  `cleanup_versions(root)`, `cleanup_staging(root)`, `cleanup_download_cache(root)`.
  Эти функции нельзя запускать параллельно с загрузкой/распаковкой обновления.
- Заблокированные Windows файлы остаются с манифестом владения для повторной
  очистки при следующем запуске. Любой неизвестный файл внутри старой версии
  блокирует удаление этой версии. NTFS junction и символические ссылки не обходятся.
- `cache/update-result.json` перезаписывается одним последним результатом;
  растущий журнал не создаётся.
- Загрузка ограничена 15 минутами суммарно и 10 секундами ожидания сетевой
  операции. `download_update` и `stage_update` принимают `cancelled=callback`;
  отмена проверяется между операциями чтения и записи, незавершённые пакеты и
  распаковка убираются. Завершённая библиотека не затрагивается.

## Границы гарантии

Механизм отката защищает замену программы. Обновления с несовместимой миграцией
базы нельзя выпускать, пока не реализованы и не проверены резервная копия и
обратимость этой миграции. На первом этапе схема библиотеки совместима с обеими
сторонами тестовой транзакции.

SHA-256 обнаруживает повреждение и подмену относительно официальных метаданных
релиза. Это не цифровая подпись Windows. Право публикации релизов остаётся
границей доверия. Обновления никогда не устанавливаются автоматически при запуске.

Остаётся узкое окно аварии между созданием нового процесса и записью его PID
helper-ом или bootstrap-ом. Если helper погиб именно здесь и нет подтверждения
готовности, невозможно доказать, что новый процесс уже завершён. В этом случае
восстановление **приостанавливается без удаления версий и медиа**. Для будущего
явного режима восстановления предусмотрен параметр
`finish_or_recover(root, confirm_no_app_processes=True)`: его разрешается
использовать только после подтверждения пользователем, что все процессы
ScriptoLib закрыты. Обычный запуск никогда не передаёт этот параметр; заведомо
живой зарегистрированный процесс блокирует очистку даже с подтверждением.
Это не сертифицированная гарантия восстановления при любом отключении питания.

## Проверка

Автоматические тесты проверяют смешанные ошибки сети и ZIP, контрольные суммы,
выход за пределы папки, повторное скачивание, безопасную очистку, таймаут
завершения родителя, успешное подтверждение, отказ запуска новой версии, порядок
остановки и отката, восстановление после прерванного helper и сохранность медиа.
В тестах процессов используются подставные процессы; это не проверка Windows GUI.

Перед первым публичным релизом нужны реальные Windows-проверки:

- установка в папку с пробелами и кириллицей;
- обновление между двумя собранными версиями, сохранение базы и медиа;
- выключение программы/компьютера во время скачивания и после переключения;
- отказ новой версии до загрузки окна и автоматический возврат предыдущей;
- поведение файлов, занятых антивирусом, и NTFS junction;
- отсутствие служебных записей приложения за пределами выбранной папки;
- удаление программы с сохранением загруженных фильмов, музыки и других медиа.
